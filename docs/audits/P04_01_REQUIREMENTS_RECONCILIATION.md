## TLS behavior and open contract

| Case | Observed implementation | Outstanding decision or verification |
|---|---|---|
| Valid leaf and issuer | `CurlHttpTransport` uses peer verification and hostname verification. `extractTlsMetadata` reads numeric expiry, libcurl expiry text or PEM validity; issuer comes from libcurl's leaf issuer field. Successful final HTTPS responses retain metadata even when the HTTP code is unexpected. | Verify the extraction matrix on the supported libcurl backends and distinguish absent, empty and malformed data. A malformed nonempty expiry string skips the later PEM branch. The PEM fallback does not supply issuer. |
| Threshold | `CheckBatchPersister` uses `expiry <= checkedAtUTC + configured days`; stored expiry/check times are second precision. `SafeHttpClient` exposes a result flag based on its own 14-day constant and wall clock. Persistence does not use that flag. | Define one authoritative configurable UTC comparison and its precision. Test one second below, equal and one second above the boundary, with default and custom values. |
| Expired, untrusted, wrong hostname or self-signed | A rejected handshake enters the probe failure path as `TLS_ERROR` for classified cURL errors, subject to earlier destination/peer safety checks. The ordinary state machine consumes failed checks. No dedicated expired-certificate incident or unverified certificate inspection path exists. | Keep strict validation and define whether normalized failure reason plus ordinary availability handling satisfies FR-5, or whether an independent TLS event is required. Existing live fixtures cover untrusted trust and wrong hostname. Add a distinct expired trusted-leaf case and an explicit standalone self-signed case. |
| Renewal and identity | Changed expiry inside the window can emit another warning. An observed expiry outside the window clears the marker and advances the cycle when a warning was active. Target URL changes reset current TLS fields and advance the cycle in [Monitor](../../app/Models/Monitor.php). | Current identity is observed expiry and monitor cycle. A new leaf with the same expiry has no independent identity. Decide if that is acceptable, and test replacement inside/outside the window and missing observations between renewals. |
| Missing metadata | A verified HTTPS outcome with no expiry leaves prior TLS fields in place and queues no fresh warning. Current fields therefore describe the last usable observation. | Define freshness and unknown presentation before exposing telemetry. Test valid, malformed, missing and restored metadata and retention of the historical warning marker. |
| HTTP and redirects | Only the terminal HTTPS hop supplies metadata. For an HTTP-origin monitor, persistence clears TLS fields even if the terminal hop is HTTPS. An HTTPS-origin monitor ending on HTTP can keep old TLS fields. An HTTPS-origin monitor can store the terminal HTTPS leaf after a host change. All hops retain the existing validation and deadline rules. | Decide whether TLS telemetry represents the configured origin or the final validated HTTPS endpoint. Verify mixed-scheme and cross-host cases and attributable metadata. Any change to allowed redirect behavior requires approval. |
| Issuer persistence and presentation | Issuer flows through [SafeHttpResponse](../../app/Support/SafeHttp/SafeHttpResponse.php) and [SafeHttpCheckResult](../../app/Support/SafeHttp/SafeHttpCheckResult.php). There is no issuer field in the monitor, check or outbox persistence contracts and no dashboard display. FR-5 requires capture but does not explicitly require storage or display. | Confirm transient capture is sufficient or approve a separate minimal persistence/display design with clear retention, length, escaping and stale-value rules. |

## Notification delivery semantics

| Scenario | Current behavior and evidence | Gap or policy decision |
|---|---|---|
| Down, recovery and flapping | One down/recovery outbox record per incident/type. IDs are deterministic for those events. Transient flaps and repeated steady-state checks produce no new event. Incident lifecycle tests cover repeat suppression. | Interpret ADR-0004's “exactly two emails” as up to two distinct incident event records when both transitions occur and an eligible recipient exists. Change the contractual wording only after maintainer review. |
| TLS warning events | TLS events have a null incident ID and unique event key scoped to monitor, warning cycle and expiry timestamp. Same expiry/cycle deduplicates; renewal beyond the window rearms. | Confirm identity and stale pending warning policy on renewal or URL edit. Current dispatcher resolves current owner and monitor; it does not validate a TLS outbox row against the current warning cycle before sending. |
| Claim, overlap and stale work | Independent dispatch uses an execution lock, bounded selection and compare-and-set claim. Cryptographic token and monotonic claim version fence follow-up writes. Stale workers cannot overwrite newer state. | Continue SQLite/MySQL coverage. Confirm shared lock store configuration on the deployment target. A fenced write does not cancel a provider call that an old worker has already started. |
| Temporary and permanent failures | Send exceptions share bounded retry behavior with exponential backoff (defaults 60 s then 120 s, three attempts total). The default claim timeout is 60 s. Missing or ineligible owner is terminal. Stale final claims reconcile to terminal failed without another send. | Provider errors currently share the same retry path regardless of permanent/transient category. Decide whether stable provider-specific signals justify classification. Verify exception, response, cancellation, and exhaustion handling with deterministic fixtures. |
| SMTP acknowledgement gap | The external send runs outside the transaction. Acceptance may occur before DB success is recorded, or a connection can fail after remote acceptance. A later claim may resend while attempts remain. A stale final claim can end in failed with acceptance unknown. Existing tests simulate the crash interval and both claim-race orderings. | Document durable event uniqueness plus **bounded retry delivery attempts with possible duplicate external acceptance and no guaranteed delivery**. A successful send record does not establish inbox delivery. Exactly-once external delivery requires an approved provider idempotency/reconciliation contract. [SMTP specification](https://www.rfc-editor.org/rfc/rfc5321#section-4.5.4.1) |
| Owner and mailer contract | At dispatch, the eligible monitor owner is resolved server-side. [Alert message](../../app/Mail/SitePulseAlertMail.php) bounds text, removes controls, and strips URL user info/query/fragment in display. The ordinary SMTP config clamps `MAIL_TIMEOUT` to 1–5 seconds. | The selected recipient is an authorized account with a nonempty address. No mailbox-verification workflow was demonstrated. FR-6 lists SMTP, Mailgun, Postmark and Sendmail. Mailgun has no mailer entry and the Mailgun/Postmark API transport packages are absent from the lock. Provider-specific timeouts and failover behavior lack uniform evidence. Log/array transports can complete locally without external delivery. |
| Scheduling and observability | Checks, alert dispatch and pruning are opt-in, with schedule and execution locks. Errors are normalized and capped; logs carry attempt/fencing state. Existing fixture evidence covers supported redaction patterns. | Review conservative logging of provider exceptions and arbitrary secret formats, apply the timeout constraint to the resolved SMTP configuration, and define operator signals for terminal failure versus acceptance unknown. |

## Proposed decisions for maintainer review

1. **TLS metadata identity and clock.** Choose the configured origin or final validated HTTPS endpoint. Specify explicit UTC second precision, a single configurable warning authority, and missing/old metadata semantics. Preserve transport safety regardless of attribution.
2. **TLS failure semantics.** Preserve ordinary availability classification for a rejected secure connection. Decide whether a separate certificate failure event is required by FR-5, what evidence it may contain and whether it warrants outbox/schema changes. No handshake downgrade or disabled verification is proposed.
3. **Issuer scope.** Keep transient capture unless an approved use case requires retention or owner display. Any persistence, schema or new presentation work requires separate authorization.
4. **External delivery contract.** Adopt bounded retry attempts and durable event uniqueness, with externally ambiguous acceptance explicitly modeled in the operator contract. Choose retry-versus-stop policy under ambiguous acceptance and whether provider idempotency is in scope. Resolve the wording in ADR-0004 and Phase 04 exit criteria after approval.
5. **Supported mailers, recipient and retry policy.** Confirm SMTP and any optional mailers, verified-address expectations, resolved timeout policy, stale TLS warning treatment and whether provider errors will be classified. Provider packages, production dispatch and topology changes require separate approval.

## Verification

On Windows with PHP 8.4.28 and SQLite, the focused run passed **241 tests and 1,507 assertions**. It selected `SafeHttpCurlIntegrationTest`, `SafeHttpClientSecurityTest`, `UrlAndIpPolicyTest`, `IncidentLifecycleAndAlertsTest`, `NotificationDispatchConcurrencyTest`, `ScheduledMonitoringEngineTest`, `HistoryPruningTest`, `OwnerAuthenticationTest` and `MonitorCrudTest`, excluding the existing named benchmark. Composer strict validation, locked platform requirements, locked audit and Pint passed. Composer returned zero advisories.

The SMTP timeout gap was reproduced locally without a connection. An in-memory Laravel mailer configured with a five-second timeout and a synthetic `MAIL_URL` carrying a 17-second timeout resolved to a Symfony SMTP stream with a 17-second timeout. This verifies precedence in the locked runtime. The test did not send mail or use production configuration values. P04-03 should verify or enforce the approved effective timeout after URL parsing.

Git whitespace and changed Markdown link checks passed. Application code, requirements, dependencies, tests, workflows and default configuration match the verified base. The draft PR records exact-head CI evidence.
